# Planner–Executor 与生成—质询审议

ResearchPilot 在原 SDM 生命周期内组织角色：Planner 负责问题、假设、实验选择及后继判断，Executor 实施确切方案并交付实际结果。方案生成者（Generator）提出和修订，独立质询者（Critic）挑战证据、反证、比较和执行条件；协作名称统一为**生成—质询审议（Generator–Critic）**。

## 角色融入哪些原职责

| 原职责 | 协作方式 | 必须分开的结论 |
| --- | --- | --- |
| 2、6：研究问题与实验协议 | 生成者提出可证伪方案，质询者检查机制、竞争解释、比较与信息收益 | 审议接受不证明假设为真。 |
| 9–13：实施与验收 | 实施线程交付真实代码；代码审议核对确切方案、变更和历史异议 | 审议不能替代确定性验收、实施后预检及授权。 |
| 18–21：证据、裁决与后继 | 共同读取来源明确的证据，质询不确定性并形成下一行动 | 模型协作不自动完成 S10，指标达标不自动产生 D05。 |

## 实际配置与协议

`agent_roles` 声明真实模型角色，参考源码的 `agent-roles.example.json`。方案生成者与独立质询者须满足现有不同模型/调用来源要求，不能用换标签伪造独立调用。`proposal_model_runner` 与 `research_worker` 读取该策略；旧字段 `a/b` 保留作机器协议。配置存在不等于实际模型调用已经发生。

新初始化采用 dialogue v4，当前研究指导为 v7。旧角色策略/冻结可能默认 v3，旧 v1–v3 和指导 v6 仍按原字节回放，不热换提示。模型是否可用以选定通道的实际能力为准；缺失时明确阻断，不静默切换。

实际模式通过原 `run_project_pipeline.py --proposal-review` 等入口及模型交接合同执行。调用 `--inspect-agent-roles` 只读配置，不执行模型、平台或训练。独立质询者可接受、要求修改、要求补证、否决或标记停滞；按结论和实质进展接续，不按固定往返轮数凑流程。

## 接受、授权与恢复

新研究在初始化、审议、回放和共同提交时共用原 S01/S02 记录校验。其余原规范接受的接入状态见 [重构进度](../SDM-REFACTOR-PROGRESS.zh-CN.md)。确切方案/代码的审议回执、执行载荷及用户授权分别核验；最终平台效果由原 Manager/Guard 管理。

前台 Codex 聊天、后台实施 Context 和模型审议调用具有不同身份；未知调用只能沿原身份对账。暂停与恢复保留原请求和完成回执，不因更名重发。此处不定义其他产品的角色系统或第二套研究引擎。完整顺序见 [从 SDM 演进的当前生命周期](../WORKFLOW-GUIDE.zh-CN.md)。


## 当前职责怎样落到两条持续会话

Planner、Executor、Generator、Critic是职责和兼容配置名，不要求各自创建一条聊天。新组件研究把问题分析、方案生成与修订、代码说明和实施放在同一研究主会话；独立质询与代码评审使用另一条持续只读会话。主会话使用已选定的方案模型实施，评审保持另一模型来源，初始化时统一相应角色配置。

原Context承接设计和实施的共同原生身份、工作轮次、锁和完成回执。会话中历史想法不是当前事实或授权；每次评审仍绑定准确对象，受控提交仍由原Manager/Guard负责。来源聊天是用户入口，不声称它与后台逐字同步。旧配置按原冻结回放，不自动合并，详见[当前协作与验证](../../skills/sdm-module/sdm-lifecycle/references/planner-context.zh-CN.md)。
