# ResearchPilot 13 步与原 SDM 21 步：演进、实现和缺口

更新：2026-11-15。以13步组织统一接受路径；实现范围和正式资格边界分别说明。

## 1. 本文的目的与可信范围

**当前 13 步是 ResearchPilot 的核心模型开发生命周期。** 项目规划、功能实现、门禁接线、异常恢复与前端展示均以这条主线组织；原 SDM 提供优先复用的规范与校验基础，原 21 步编号用于解释来源。核心流程定义、程序已实现能力和实际验收证据分别报告。

13 步是当前版本的项目约定。任务可复用有效证据、整合执行活动或说明不适用工作；核心目录若需增删、拆分、合并或重排，应在版本变更中同步说明理由、实现/门禁影响、兼容方案和验证。未实现、缺证据与不适用必须分开，不能据此绕过原授权或未知请求对账。

本文解释为什么从21步组织为13步、实际怎样落实、得到哪些效果、哪些仍未完成。原始对比基线为本地保留初始模板`ec870b0e12b0932741a193520a004cba5ae9f3c3`（2026-09-18），不代表已核实独立上游最新版本。原规范身份见[原生命周期定义](../assets/lifecycle-steps.json)；当前核心定义见[13步目录](lifecycle-map.json)。

阅读时区分三层：**核心流程定义**说明项目如何组织；**代码接线**说明实际调用了什么；**验收证据**说明在哪个版本/任务/环境实际验证过。流程名称、模型同意、阶段位置都不能补造科学接受。


当前执行入口、适用范围和代码接受路径以[统一治理说明](sdm-governance.md)为准。新项目与既有二分类研究共用一条接受路径；旧冻结保留原规则。以下合并理由继续适用，历史批次验证数字仅证明当时范围，不能作为本次真实训练验收。

## 2. 为什么这样合并

合并依据是共同输入、交付对象、职责所有者和实际接续边界，不以凑到13为目标。本版将八组相邻活动分别合并，共减少八个目录项；其他五项保留独立边界。原科学职责未在本批删除，后续执行、审议、恢复和前端能力归入相应步骤。

| 当前核心步骤 | 原SDM步骤及名称 | 调整依据 |
| --- | --- | --- |
| 1 明确目标与可证伪问题 | 1 提出业务问题；2 定义可证伪研究问题 | 合并原问题提出和研究问题定义：它们共用一份需求背景，在同一研究意图准备活动中交付。 |
| 2 核对数据、评价契约与执行范围 | 3 关闭 ML Contract 语义 | 保留原契约步骤，将平台能力和执行范围的现有实现纳入同一准备活动；权限仍贯穿后续。 |
| 3 明确比较起点与基线依据 | 4 定义 Baseline；5 复现并锁定 Baseline | 承接原比较定义和基线管理职责，区分探索起点、实际比较对象与阶段基线；复现、锁定和替换按证据进展处理，不要求首轮即确立稳定基线。 |
| 4 设计实验与运行计划 | 6 创建 Experiment、HPO 与 Run Plan | 保留原实验设计边界；将生成—质询作为其协作实现，不单列新的科学阶段。 |
| 5 检查就绪并固定实验依据 | 7 数据与方法 Readiness；8 冻结 Experiment | 合并就绪和冻结为一次执行准备交付，保留“先就绪、再固定”的内部依赖；不将两种接受混成一个布尔值。 |
| 6 准备上下文并实施变更 | 9 拆 Engineering Stories 与 Context Packs；10 Coding Agent 实现 | 合并任务拆分与编码：它们在同一实施作业中衔接，准备和实际完成仍分别可追溯。 |
| 7 审查代码并完成工程验收 | 11 代码与契约审查；12 确定性工程验收 | 合并工程交付的审查和验收，保留审议判断与确定性事实两个证据来源。 |
| 8 执行实施后预检 | 13 实施后 Preflight | 保留独立的实施后边界，因为它依赖实际实现和环境，不能在方案讨论时预先通过。 |
| 9 登记运行并受控提交 | 14 物化不可变 Run | 保留提交身份边界，与长时间观察分开，避免把提交请求、平台 UID 和训练完成混为一谈。 |
| 10 观察训练并回收执行结果 | 15 HPO、独立确认训练与执行编排 | 展开原训练编排的真实等待、回收和恢复能力；这些是职责内部扩展，不另设科学通过标准。 |
| 11 核验评价与适用专项结果 | 16 锁定评测；17 鲁棒性评测 | 合并评价交付：常规与专项可在同次结果核验中说明，但各自适用性与证据不能互相替代。 |
| 12 汇总证据并开展独立审查 | 18 构建 Evidence Bundle；19 独立 Evidence Review | 合并证据准备与审查为一个证据交付步骤，保留“先汇总、后独立审查”和各自证据身份。 |
| 13 形成结论并决定后继或归档 | 20 产生 D05 Scientific Decision；21 创建后继实验或归档 | 合并结论和行动交付，使决定有紧邻的证据依据；科学裁决、目标状态和后继授权仍分别保留。 |

保留独立的契约、实验设计、实施后预检、提交身份、长时间执行职责，是因为它们的输入和失败处理不同。例如：提交请求已登记与训练结果已取得属于不同事实；实施后的功能检查不能在科学方案讨论时预先通过。

合并后的步骤可以包含多个内部检查和回执。例如当前步骤7同时承接代码审查与工程验收，两类证据仍各有来源，最终沿同一SDM规范推进。当前步骤13连接结论与行动，科学裁决、目标状态及后继授权仍分别判断，不把其中一项同意扩大为全部权限。

## 3. 13步实际执行、门禁与缺口

本节中的“已接”指具体范围内的代码控制；不表示整个活动已通过原规范全部接受。代码链接指向实际脚本，原规范对象编号只是来源身份。

### 1. 明确目标与可证伪问题

**输入与产出：**用户目标、约束、非目标、现有结果和问题来源 → 需求 S01 与研究简报 S02；目标、假设、机制、反证和不确定性。

**怎样执行：**项目发现和渐进引导准备实际输入；research_intent 构造原 S01/S02，初始化、方案/代码审议、回放和共同提交调用同一原校验。

**已接控制：**新初始化在文件/冻结/外部效果前检查原S01/S02；方案/代码审议、回放和共同提交共用同一检查。S02绑定完整S01记录摘要，拒绝用passed字段替代实际内容。

**规范缺口：**记录接受已接；回执明确transition_accepted:false、execution_authority:false，尚不产生完整账本转移、签名或锚定。

**失败与接续：**问题不清则澄清，假设/反证不足则修订；不以模型同意覆盖缺项。

**代码依据：**[research_initialize.py](../scripts/research_initialize.py)、[research_intent.py](../scripts/research_intent.py)、[proposal_model_runner.py](../scripts/proposal_model_runner.py)。

### 2. 核对数据、评价契约与执行范围

**输入与产出：**研究问题、系统/数据事实、划分、评价器、平台能力和用户授权 → 适用契约、数据与评价身份、资源/权限范围及未闭合项。

**怎样执行：**复用原 G 契约规则；项目接入固定数据、划分、输入输出和评价事实；执行接入的实际能力与用户范围分别核验。

**已接控制：**统一治理输入生成并验证原G01/G02/G03/G07/G08/G09/G10/G13；核对实际数据、划分、标签、张量、契约引用和平台范围。

**规范缺口：**当前项目事实可接入规定多类分类与标量回归结果，既有固定长度一元二分类保持原规则；空间/标定/同步、稳健性和部署不在本适配器资格范围，要求这些职责的任务不能静默省略。原平台签名数据操作不冒称已执行。

**失败与接续：**缺契约/数据事实先补齐；范围变化重新核对，不能用“当前未实现”代替“不适用”。

**代码依据：**[contracts.py](../scripts/contracts.py)、[component_pipeline.py](../scripts/component_pipeline.py)、[required_skills.py](../scripts/required_skills.py)、[component_submission.py](../scripts/component_submission.py)。

### 3. 明确比较起点与基线依据

来源仍为原SDM第4步“定义Baseline”和第5步“复现并锁定Baseline”。调整的是职责的完成时点与表达：先定义探索起点、数据和评价条件，沿步骤4–11取得有效结果；已有可信证据可复用。后继通过原审议选择具体比较候选，实施前再次核对原决定、结果、协议和原配方。步骤13可提出保留、回退或更新比较依据，再回到第3步处理阶段基线及必要复现。

第一轮不是永久固定基线，当前最优候选也不自动获得稳定性或正式资格。原B01定义、B02锁定、B03复现、B04替换/停用职责保留；当前普通工作链不具备的完整签名锁定资格继续列为缺口，不以改名补标通过。

实际入口是component_candidates.selected_reference与原validate_decision、validate_accepted_direction，以及原round_evidence和配方读取；后继实施使用同一结果。离线控制覆盖选第2轮而非第1/第3轮、低分首轮可作为探索起点，以及对象/协议/配方替换阻断。

### 4. 设计实验与运行计划

**输入与产出：**研究问题、适用契约、探索起点或已核验比较对象、历史证据与预算 → 干预、对照、预期观察、判断规则、搜索/确认运行及成本计划。

**怎样执行：**生成—质询审议在共同证据上形成可证伪方案；指明实际基线、竞争解释、结果分支和变更影响。

**已接控制：**原E01科学字段投影与变量检查、第6步行门禁及原可执行科学规则校验已接；原候选预算扩展为可从首轮计数的有界研究。

**规范缺口：**投影科学内核不是完整E01锚定工件；本适配器不支持正式HPO/确认运行资格。目标阈值不能代替原科学裁决条件。

**失败与接续：**拒绝或缺证据时修订/补证；问题、契约或基线不成立时回到步骤 1–3。

**代码依据：**[research_replan.py](../scripts/research_replan.py)、[proposal_review.py](../scripts/proposal_review.py)、[proposal_model_runner.py](../scripts/proposal_model_runner.py)、[contracts.py](../scripts/contracts.py)。

### 5. 检查就绪并固定实验依据

**输入与产出：**待执行方案、数据/方法就绪事实、预算及需固定的版本 → 就绪结果、固定协议依据及冻结运行时引用；各自接受范围单列。

**怎样执行：**检查数据、方法和平台条件，固定确切方案/代码/指引/规范摘要。原 26 份规范依赖进入新冻结。科学协议接受、运行时冻结和实施后预检分别记录。 初始化固定执行代码可先于模型审议；这属于宿主启动准备，不表示科学协议已接受。本步的科学就绪与协议接受仍按各自实际证据判断。

**已接控制：**运行时、指引、原26份规范依赖、适用契约、科学内核和预算被固定；科学/代码两次审议绑定同一治理依据，缺少事实不会成为通过标志。

**规范缺口：**不产生原E02/S04正式权限消费、Git冻结和账本锚定资格；任务分配、远端预检和完整拟合的不同边界分别记录。

**失败与接续：**缺就绪事实返回对应所有者；固定后的语义变更按原变更/后继规则处理，不改旧冻结。

**代码依据：**[research_runtime.py](../scripts/research_runtime.py)、[research_intent.py](../scripts/research_intent.py)、[component_pipeline.py](../scripts/component_pipeline.py)、[specctl.py](../scripts/specctl.py)。

### 6. 准备上下文并实施变更

**输入与产出：**确切方案、受保护接口、允许文件、已有 Context 和验收要求 → 实施任务/上下文、实际代码差异、版本与变更交付。

**怎样执行：**从方案准备受限实施合同，复用原 Context，由官方 Codex SDK 原生实施线程产出实际改动并交付；不以审议文字冒充代码。

**已接控制：**实际实施继续复用原Context、已接受方案、允许文件/配置、原生完成回执和纠错路径；统一治理依据进入科学和代码上下文。

**规范缺口：**不把普通原生实施回执冒充完整S05/S06/E05签名工件；能力不支持时返回补证或重规划，不能改受保护评价绕开限制。

**失败与接续：**上下文不足先补齐，实施失败返回对应任务；能力缺口由原反馈路由处理。未改代码时复用仍有效的实施证据。

**代码依据：**[research_implementation.py](../scripts/research_implementation.py)、[research_context.py](../scripts/research_context.py)、[implementation_validation.py](../scripts/implementation_validation.py)。

### 7. 审查代码并完成工程验收

**输入与产出：**实际差异、确切科学方案、接口契约、历史异议和验收证据 → 代码审议回执、确定性工程验收结果和待处理问题。

**怎样执行：**独立质询核对方案忠实性和变更影响，必要的确定性检查提供实际行为证据；工程 CI 与代码审议分别记录。

**已接控制：**代码审议通过原回执回放，实际文件/语法/载荷/允许范围固定；与后继科学方案和统一治理依据绑定，远端功能证明单列。

**规范缺口：**compile和审议不能替代功能验证；通用工程CI与原正式S07/S08组织审批不由本组件伪造。

**失败与接续：**重大异议未闭合返回步骤 6；缺检查先补证，不用审议接受覆盖失败。

**代码依据：**[proposal_model_runner.py](../scripts/proposal_model_runner.py)、[component_submission.py](../scripts/component_submission.py)、[implementation_validation.py](../scripts/implementation_validation.py)、[scm_ci.py](../scripts/scm_ci.py)。

### 8. 执行实施后预检

**输入与产出：**实际代码/配置、固定方案、执行环境及适用功能/恢复要求 → 适用的张量、有限值、微型运行、恢复与平台准备证据。

**怎样执行：**提交前先核对实际代码、配方和平台条件；功能预检在授权远端任务内先于正式拟合执行，恢复初始状态后才训练。步骤9包含为预检分配远端任务，因此物理调度会与步骤8交错；只有真实证明回收后才将步骤8标记为已核验，不预先通过，也不额外创建一份预检任务。

**已接控制：**项目工作负载执行其固定的适用功能检查，回收并按同一验证器重放；既有二分类保留张量/有限值/梯度、微型拟合、序列化接续及初态检查。项目结果为五项产物，原二分类四产物格式保留。

**规范缺口：**这是已实现的远端程序，只有真实运行回收后才能宣布该次通过；本地结构/运输替身检查不是PyTorch或平台实训。几何不适用有范围依据，完整原S09平台签名未冒称。

**失败与接续：**预检失败不得进入正式拟合；修复影响协议时回到步骤4/5，新代码重新审议和核验。已提交的失败或未知任务仍计入原预算。

**代码依据：**[research_implementation.py](../scripts/research_implementation.py)、[component_payload.py](../scripts/component_payload.py)、[lpai_manager.py](../scripts/lpai_manager.py)、[component_submission.py](../scripts/component_submission.py)。

### 9. 登记运行并受控提交

**输入与产出：**固定运行计划、当前实现、提交前检查、已固定的远端功能预检、确切审议回执和真实授权 → Run/Attempt 与确切提交身份；平台读回或待对账状态。

**怎样执行：**首轮和后继进入同一 component_submission 边界，核对意图、审议、载荷和授权，再由 Manager/Guard 处理平台效果。

**已接控制：**首轮/后继共用原提交校验和统一契约/科学内核接受；Run/Attempt在Manager.apply之前落盘，原Guard对账和暂停门禁保留，失败/未知不释放预算。

**规范缺口：**普通运行登记不等于原R01/R02正式指纹/运行计划资格；额外正式职责须经其原接受路径，不能用新身份掩盖未知结果。

**失败与接续：**缺前置事实阻断；结果未知禁止换 key/通道重提，也不为未知旧请求补一轮新审议后重发。

**代码依据：**[component_submission.py](../scripts/component_submission.py)、[lpai_manager.py](../scripts/lpai_manager.py)、[submission_guard.py](../scripts/submission_guard.py)。

### 10. 观察训练并回收执行结果

**输入与产出：**同一平台 UID、原请求/Attempt、预算和执行计划 → 平台终态、原始产物、失败/取消/未知证据及唯一结果交接。

**怎样执行：**官方 SDK 与原事件源观察同一任务，持久退避，终态后回收产物并登记分析作业；监督、收件、在途排空和恢复在此保障连续性。

**已接控制：**复用原ComponentSource与Manager/Guard，绑定相同UID、namespace、原计划、实际配置及完整产物；失败诊断保留真实平台终态，不当成有效候选。

**规范缺口：**未终结/结果未知不能科学收口；故障原因未获证时不一律称为系统失败，不能由超时或理由字符串捏造终态。

**失败与接续：**暂时读取失败退避；未知先对账；已知准备失败进入修复，不赋低分或伪装有效训练结果。用户暂停阻止新派发。

**代码依据：**[component_event_source.py](../scripts/component_event_source.py)、[lpai_manager.py](../scripts/lpai_manager.py)、[research_supervisor.py](../scripts/research_supervisor.py)、[component_pipeline.py](../scripts/component_pipeline.py)。

**已接控制：**原结果校验重算预测指标、核对固定split/selection、源数据、代码与实际参数；预检证明必须匹配冻结策略。

**规范缺口：**本适配器不声称未触碰测试集、设备/时间分组、稳健性和部署资格；要求这些额外结论时需实际增加供证能力。

**规范缺口：**原模型调用独立性不冒充组织级签名审批；普通完整账目/原件引用不自动等于D01–D04正式工件出版或S14权限消费。未决偏差阻止接受。

### 13. 形成结论并决定后继或归档

**输入与产出：**已审证据、固定判断规则、目标/预算、授权和用户最新指示 → 科学结论及限制；继续、补证、修订、回退、停止或归档的明确决定与血缘。

**怎样执行：**保留原科学裁决；原候选规则选择实际比较对象及下一行动，积累证据后可提出阶段基线，按适用的原复现、锁定和替换规则回到步骤3。后继沿同一Context/Guard接续，不将当前最优直接晋级为正式基线。

**已接控制：**使用原evaluate_scientific_decision、冻结规则及全量终态账目；接受方向/状态绑定原审议提案。数值目标与科学裁决分别记录，后继返回同一实施与提交链。

**失败与接续：**需要后继回到步骤 1–5 中受影响环节，必要时补测；范围或授权变化重新核对，归档/关闭按原规则。无固定轮数自动停/续。

## 4. 三条关键调用链证明了什么

### 4.1 需求/研究问题复用原记录门禁

`research_initialize.prepare → research_intent.prepare/check → lifecycle_rules.check_records → 原AssetBundle.validate_artifact / _semantic_step_checks / evaluate_gate`。

[research_intent.py](../scripts/research_intent.py)绑定完整S01记录摘要，真实构造S01/S02；[lifecycle_rules.py](../scripts/lifecycle_rules.py)读取原步骤行gate，调用原schema和共享语义。`specctl`使用同一共享语义，没有在组件目录再复制一套近似判断。回执明确`transition_accepted:false`、`execution_authority:false`，拒绝 caller 伪造S12/S13/S14授权/平台回执。

### 4.2 首轮和后继共用操作提交边界

`ComponentPipeline.dispatch_submission → component_submission.verify → Manager.apply / 原Guard`。Guard已有意图时先走`Manager.reconcile`，不新建科学审议或再次提交。

[component_submission.GATE](../scripts/component_submission.py)包含六项操作条件：方案审议、代码审议、已审载荷、比较/范围、提交动作及原始委托授权。审议回放使用原`proposal_model_runner.drive(verify_only=True)`；确切载荷、种子意图、范围和授权各自核验。

注意：名为`manager_preflight`的叶子只检查`task.submit`动作。[Manager.apply](../scripts/lpai_manager.py)写前还会重新核对配置和原计划。这些控制不能替代原就绪、工程验收或S09的全部科学事实。

### 4.3 平台成功后仍须核验结果

`ComponentSource → component_results.verify → 结果就绪事件 → 证据分析/后继`。

[component_results.py](../scripts/component_results.py)核对原Manager回执、任务/组件身份、实际载荷、产物和协议，依据原始预测重算指标；缺产物、错划分或指标不符时拒绝有效结果。[component_candidates.py](../scripts/component_candidates.py)据已核验结果选择候选、判断登记目标，尚不等于消费完整D05。

## 5. 首轮、后继和异常如何走

首轮在当前步骤1–5准备问题、契约、基线定义与实验方案，按实际变化实施或复用工程证据，经代码审议和共同提交，再观察、评价、审查证据及决定后继。首次训练本身用于建立基线时，步骤3只能登记候选定义，步骤9–11取得实际证据后再确认。

初始化冻结执行代码是启动宿主的准备动作，可以早于模型方案审议；科学协议接受与运行时固定分别记录。13步描述职责依赖，不要求后台出现13个同名状态或每轮重新调用13次。

后继通常从步骤10–13取得实际结果和判断，返回受影响的步骤1–5；必要时实施/验收后再提交。已有有效基线和未受影响工程证据可以复用。数据、评价器、模型接口或资源/授权变化时，重新检查相应职责。

用户暂停阻止新派发，未知平台/模型请求只沿原身份对账；已知准备失败进入修复，不赋低分。单项Study结束与项目目标完成分开，固定轮数不是自动结束依据。Context、事件收件、监督、排空和恢复是贯穿流程的能力，不新增平行科学通过标准。
