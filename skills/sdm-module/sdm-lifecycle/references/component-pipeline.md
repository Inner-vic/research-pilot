# Component research pipeline: waiting and native continuation

## Public preparation, readiness and closure

For a fresh study use `research_initialize.py --spec STUDY --destination NEW_MODULE
--store NEW_STORE --workspace NEW_WORKSPACE --output NEW_CONFIG`. Pin the public
data checksum, split, actual target provenance and strong justified baseline.
An optional `training_limits:{min_epochs,max_epochs,default_epochs}` narrows the
10–30 epoch default to the actual confirmed scope (e.g. all three equal 20).
The initializer validates it before any freeze/asset operation and binds it in
the original delegation and all successors. A narrower confirmation must not
silently become the broader default.
An explicit `dataset_input:{spec:REF,state:PATH}` prepares one official SDK data
asset, journals its writes, and verifies uploaded bytes before using its mount.
It does not submit training; the resident owns the first submission and all
successors. Never rename an unknown request to test a corrected input.

A failed task before any valid baseline is a preparation diagnosis, not a zero
score/candidate or a completed research round. Publish `initial-failure.json`
and `needs-attention` before opening a science/model intent. Preserve the failed
UID and repair the actual data/environment prerequisite. Public-source fetches
are bounded/checksummed and retain identity-bound partial bytes; local access
does not prove compute-node access. Prefer verified official mounted input when
external downloads are unavailable remotely.

Use `research_chain.py --config CONFIG` to audit actual producer/result hashes,
parent/base tasks, original frozen reviews, native context and successor writes.
Report initial ownership, adaptive edges and reproduction evidence separately;
successful recovery alone does not qualify a new adaptive research chain.

Code review must foreground the complete protected trainer, decoded launch proof
and current execution binding before large historical recipe inventories.
Show the complete qualified shell/Python wrapper with only its compressed
literal omitted, literal/raw/file hashes, same-role command check and actual
parent/successor wrapper-template comparison. A command digest alone does not
explain execution fidelity. Keep raw requests registered; do not add base64
copies to every prompt, grow input limits or manually approve a blocked gate.
Retain original receipts; upgrade only an idle host to a new frozen version,
with actual first-task/history identity preserved.

The critic packet already contains prior critiques. `proposal_input.py` removes
only duplicate critique copies and machine-generated evidence indexes from the
transport, preserving full proposal text, rationale, raw source indexes and
registered supplements. It binds and revalidates original accepted receipts,
then restores the exact full history for challenge/approval validation. No
lossy model summary, raised input limit, automatic approval or replay of a known
completion is permitted. A different cause of budget exhaustion can still block.

Each coordinator save publishes `progress.json` and `PROGRESS.md` in its own
component-pipeline directory. These derived views distinguish actual results,
the retained incumbent, current task, normal waiting and `needs_intervention`.
The ledger is committed before derived health/progress. Health is bound to the
same configuration/state; result-collection errors must be visible as requiring
reconciliation, rather than showing an old running observation as healthy.
Official task and Pod timestamps may be out of order. Query the exact UID/Pod
across all retained lifecycle timestamps, then retain the original artifact,
identity and metric checks; a platform success alone never substitutes for them.
Projection errors are reported separately and cannot retry or halt a research
operation. The original ledger and immutable results remain authoritative.
Incumbent trajectory/error overlap is supplied to both scientists; repeated
failed changes must inform mechanism assessment and decision value. The counts
are descriptive and never create a numerical stopping budget.

`research_runtime.py --config OLD --destination NEW_RUNTIME --new-root NEW_STORE
--output NEW_CONFIG [--state OLD_STATE] [--patch PATCH]` adopts only a known task
after its original host has exited, native context has no pending turn and all
original jobs are completed. It preserves original Guard/UID and governing
accepted plan. The bounded patch cannot replace execution identity or resources.
Preparation journals the frozen configuration, validates it with its own frozen
verifier and commits idempotently. Retry the same input/output; do not hand-edit
an active database or recompute a new intent after an unknown outcome.

`research_runtime.py --config CONFIG --readiness` performs an official read of
the exact component and identity before any model/platform write. Opt-in
`runtime_readiness:{version:1}` also gates service startup. Network permissions
are a host boundary: an inaccessible sandbox is not a platform approval request,
and the service cannot grant itself OS network permissions.

`completion_shutdown:{version:1}` exits the owned local host only after a typed
pipeline terminal state, all Inbox jobs completed and no pending native turn.
It writes `completion-exit.json` and never stops platform resources. Attention
or unresolved states do not become successful completion. Restarting that same
config after a known-UID idle wait preserves its original Guard and native
Context; public `pause` also survives restart. This is recovery after a host is
started, not OS service management or automatic startup after power loss.
Initial host/network permission provisioning remains an explicit host concern.

`implementation_feedback:{version:2}` requests a bound `status:"blocked"`
implementation JSON with a typed block_kind, reason and registered evidence
paths. The host does not depend on Markdown prefixes in that mode. Legacy
prefix handling stays opt-in v1; a model's claim never extends authority.

Policy v3 is an explicit operational reproduction objective, separate from an
already achieved quality goal: until-verification, baseline_result and scope_ref
bind the exact known recipe. Original inventory permits only that baseline
match while no reproduction intent already exists. A new actual UID must match
complete epoch histories, selected epoch and row-aligned predictions/probabilities.
A mismatch requires diagnosis of that UID rather than blind resubmission.
This does not invent a higher quality target or a normal research trial quota.
The coordinator supplies `execution_contract.next_round` as new task metadata;
even an unchanged scientific reproduction must use that value. A completed
implementation with the old round number returns typed validation feedback
before packaging or any platform submission.

## Candidate-aware, goal-driven version 4

### Integrated host and workload operation

For a new study use `research_initialize.py --spec STUDY --destination NEW_MODULE
--store NEW_STORE --workspace NEW_WORKSPACE --output NEW_CONFIG`. A
`sdm-research-initialization/v1` spec supplies project_id, source_ref, objective,
immutable template/manager_config/request_template/baseline_source/baseline_model
references, comparison_identity, training, target and workload. The initializer
does read-only official preflight, never submits or calls a model. It creates
independent control/workspaces/Context, a frozen payload, exact original Manager
plan and bound standing delegation. Repeating identical inputs reuses the
prepared configuration; changed inputs cannot overwrite that identity.

`initial_submission:{version:1,authorization:REF,confirmed_plan:REF}` is an opt-in
fresh-study entry. The original resident applies its first Manager plan only
while its original Guard is new; every other phase reconciles the same intent.
An initial-dispatch marker binds host/config/plan before calling the Manager.
Initial observation and every adaptive successor use the same provider path;
an external bootstrap submission is not required. Empty known_task_uids means
an empty new-study ledger for continuous policy v2, never zero remaining budget.

`research_chain.py --config CONFIG` audits immutable actual artifacts, original
scientific/code model receipts, native turn and Manager plan links. It separates
the chronological trigger from the selected experimental base, compares actual
recipes and verifies same native thread within one frozen host. A reproduced
recipe cannot count as an adaptive successor. Terminal resident publication
writes `component-pipeline/continuous-chain.json`; the count describes evidence,
not a research budget or a reason to continue an already achieved goal.

Public data preparation may use `public_dataset_source.fetch` with a pinned
HTTPS source and checksum. Bound partial files permit HTTP Range continuation;
ignored Range restarts a GET, never a platform write. Total deadlines, byte
limits and progress are explicit; only complete checksum-verified content is
published. A slow data fetch is not model fitting. Keep TEST outside an adaptive
validation study unless its use is independently specified.

Freeze the complete source bundle, then run `research_supervisor.py --config
CONFIG` from that frozen runtime. One OS lock owns the supervisor; the child
joins its Windows Job before loading the event service. Process exit drives
recovery of the same frozen config, database and Context. Durable completed
native receipts can finish original bookkeeping without another model turn.
An unresolved model/turn or missing receipt stops for original reconciliation;
the supervisor never submits, changes a model identity, or grants authority.
Repeated identical failure without state progress stalls. Normal exit, explicit
public stop and achieved-goal completion never start a replacement child.

`research_supervisor.py --config CONFIG --inspect-recovery` and
`research_status.py --config CONFIG` are read-only inspection entries. The live
service also accepts `--control overview` and authenticated `/overview`; this
projection excludes prompts, bearer tokens and credential values. Frontend
display is separate from dispatch and task completion never waits for a chat.

`research_host_install.py --config CONFIG` previews a concrete per-user login
deployment. Only its explicit `--install-login` creates the uniquely bound OS
task; `--uninstall-login` removes that same owned task. It uses normal user
permissions and pythonw, triggers only on login and is unrelated to Codex's
paused periodic automation. Installation, observed host restart and actual OS
login/power-loss recovery are three different claims. Do not mark installation
or OS recovery successful from preview output.

A deployment helper can be a separately frozen operational bundle targeting
an older frozen host; both manifests are checked independently, without
rewriting the original host. The read-only status projection also exposes the
current persisted Task UID, last known provider status, observation errors and
age; cached status must not be presented as an instantaneous provider query.

An opt-in pipeline `workload:{version:1,adapter:"binary-component/v2",
training_loss_hook:true,seed_values:[42],source_ref:USER_SCOPE}` exposes
`build_training_loss(config)` in model.py. It supplies a scalar finite training
criterion only; protected validation still uses CrossEntropyLoss with the same
split, metric and checkpoint selection. Model/optimizer/loss and allowed seeds
are scientific dimensions; other trainer hooks, data/evaluation changes and
platform actions remain outside this ABI. Missing capability returns structured
feedback, not permission to alter protected code. Other task types remain
unqualified until their own result and payload adapters are validated.

Explicit reproduction scope v2 additionally binds
`prior_completed_recipe_uids`. Every matching prior recipe must be exactly in
that list and succeeded; any extra/active match blocks a new intent. Only with
the new protected loss ABI can the exact trivial function
`def build_training_loss(config): return nn.CrossEntropyLoss()` normalize to
the legacy default loss for duplicate detection. All other AST changes remain
distinct; this exception is not general code equivalence. The full remote
trajectory and predictions still decide actual reproduction success.

`recovery_exercise` is an explicit opt-in local interruption exercise, bound to
the config/source instruction with durable one-shot markers. Its supported
checkpoints are a native receipt already saved and a known submitted-task wait.
It cannot inject an unknown external POST, stop a remote task, repeat a model
call or supply a scientific decision. Ordinary runs omit it.

New frozen `component_pipeline.version=4` accepts `decision_policy` version 2
for user-requested continuous research: `target:{metric:"validation.macro_f1",
operator:">=",value:PROJECT_TARGET}`, `budget:{known_task_uids:[...]}`, and
`termination:{mode:"until-target",source_ref:USER_INSTRUCTION}`. There is no
submission-count ceiling; costs remain accounted. Unmet goals cannot become
stop-research because a trial count was reached. Do not choose a validation-only
budget on the user's behalf. Existing pause, authority and unknown-result gates
still block unsafe or unresolved actions.

Only an explicitly bounded scope uses `decision_policy` version 1:
`target:{metric:"validation.macro_f1",operator:">=",value:PROJECT_TARGET}` and
`budget:{known_task_uids:[...],max_new_submissions:PROJECT_BUDGET}`. This adapter
currently qualifies binary fixed-validation macro-F1 only. It generates the
candidate registry from verified artifacts, preserves the incumbent across
regressions, supplies both latest and incumbent executed source, and binds the
approved `candidate_decision.base_task_uid` through selected-base implementation
and code review. Choices are continue, rollback, redesign and stop. Rollback is
a recipe base for a new informative intervention, not a deployment or a repeated
historical task. Weights are references, not implicit warm-start authorization.

All observed newly submitted UIDs, including failed and cancelled attempts,
consume the frozen budget. Goal attainment and budget exhaustion are distinct
typed exits; an exhausted below-target run must retain its best candidate and
state that the quality goal was not achieved. `minimum_rounds/revisions` remain
chain diagnostics, never the v4 scientific stopping condition. The original
Manager, Guard, unknown-result reconciliation and dual-model review still own
their respective gates. Existing v1–v3 runtime/configuration semantics remain.

Current delivery priority: qualify the connected loop with real training and
result-driven successors. Preserve/reconcile already-submitted tasks; more
control tests do not replace the requested scientific rounds.
Official lpai Skill remains required; it is not replaced by a custom Skill.

## Research loop and authority

For new v4 freezes, supply the full protected trainer and execution contract
before science review. Required diagnostics must be implementable through that
interface; an approval cannot grant edits to protected trainer files. An opt-in
completed implementation response beginning `needs-agent` or `needs-capability`
is preserved as an untrusted, receipted implementation-gap report and returned
to independent scientific review in a new immutable continuation folder. Do
not classify an explicit refusal as a stale-manifest repair. Both reviewers
must assess its claim against the actual interface and historical evidence.
Unknown turns still reconcile only; this path does not retry an unknown call,
allocate resources, extend authority or count an unimplemented idea as training.
Scientific review also receives a compact verified history of actual model
source, training settings, interventions and metrics. Metric-only summaries
cannot establish novelty. Preserve completed implementation refusals across
attempts and idle host handoffs, so the next review does not rediscover the same
unsupported or previously completed recipe. Original recipe/Guard checks remain.

Codex + SDM owns scientific choices: plan/critique → implementation/freeze →
original Manager/Guard submission → durable wait registration → terminal
observation → artifact verification/archive → native Codex continuation →
result assessment and next plan. A finished experiment does not finish research.
Do not pre-create research branches or pre-write improvements before results.

The host handles observation and reliable delivery. It must not choose models,
change research goals, convert queue delays into training failures, resubmit an
unknown write, or treat a platform success status as a valid result. New execution
still passes the original preflight, current authorization and Guard. Platform
approval is a separate wait state; it cannot be bypassed by a completion event.

## Submission confirmation and channel selection

Keep the user's research delegation, the selected official transport and the
platform's returned approval state separate. Reuse still-valid explicit user
authorization within its scope; do not add a recurring SDM confirmation or chat
acknowledgement requirement to every successor. Required task information must
still describe the actual reviewed experiment.

Do not infer that every component submission requires Feishu approval because
one Agent CLI request returned pending_approval. Official SDK submissions and
Agent CLI submissions have different interfaces and authentication. Historical
SDK success is useful evidence to investigate, not qualification of the current
host or permission to switch a pending request to SDK. Qualify any direct
submission channel against the current official Skill, identity, permissions,
exact payload readback and existing Guard before choosing it for a fresh run.
Never change an active intent's transport or retry it through a second channel.

For explicitly selected SDK research, completion source v3 freezes the transport
against the Manager and original plan, including every successor. Freeze all
three resources from `guidance_sources()` at their runtime-relative paths and
declare their hashes before starting a new host. Pass the actual delegated
epoch/resource/duration limits into both scientific roles, not only the later
execution guard. An approved proposal outside those limits remains unexecuted
and must be revised; it cannot count as an experimental improvement.
Include independently decoded packed-file identities in the code-review sources,
not only the builder's claimed hashes. A cold runtime handoff at a known task
wait may retain `verified_history` and its original accepted successor plan:
revalidate every archive and fair-comparison identity, keep the same current
task/Guard and native Context, and leave the old database intact. This never
permits replay of an unknown platform or model request.
Pause stops new dispatch, not an SDK request already past its intent boundary.
Read the post-action status and reconcile any in-flight response before claiming
that a task was not submitted. Host-owned split/nonfinite checks belong in the
protected trainer; keep model plugins free of caller-frame access and trainer
mutation. Preserve the code actually executed by every earlier task.

An enabled projects.start permission does not prove an approval exemption or
that the configured local Key belongs to the Agent shown on a web page. Inspect
official permission/confirmation settings read-only first; do not silently
expand permissions, disable approvals or copy credentials. Notifications alone
do not establish which task started: reconcile the original intent to its UID.

## Wait contract

New source v3 can opt into
`result_identity: {version: 1, mode: original-manager-native-config}`. Bind the
original immutable Manager plan when verifying terminal artifacts. LPAI may
fill workflow/catalog/PVC/default fields after the initial verified readback;
whole-response data hashes can therefore change without a submitted command or
resource change. Reuse the original Manager's native configuration comparison
and exact task/parent/name/scope checks, retain both raw digests and the plan
reference in the result, and still verify code/data/split/predictions/checkpoint.
Never accept a real image, command, role, resource or mount mismatch. Legacy
sources retain raw-digest behavior; do not rewrite their original receipts.

Terminal pod log reads must include `--start`/`--end` derived from the actual
task/pod creation/start and finish/update timestamps, as required by the
official lpai Skill. The default recent window can silently omit old preflight
and artifacts after a long wait or restart. Include earlier pod creation when
SDK task start is later. Empty/incomplete logs remain an evidence-read failure,
never grounds for training replay; retry the same UID and observed window.

Keep platform/observation state separate from model execution:

| Phase | Host action | Model call |
| --- | --- | --- |
| pending approval | original-intent read-only reconciliation | none |
| queued/preparing/image pulling | official CLI state reads; persisted slower cadence | none |
| running | official CLI state reads; bounded progress evidence | none |
| terminal observed | collect original task artifacts; retry incomplete reads | none yet |
| result ready | commit evidence manifest and one durable delivery | native tool output |
| failed/unknown result | preserve evidence, distinguish task failure/read failure | one actionable diagnosis when ready |
| model running | serialize original context; retain thread/turn receipt | no second concurrent turn |
| next plan accepted | implement/freeze/register with original Guard | SDM/Codex decisions |

With the currently qualified official CLI, component completion push has not
been established. Host polling is the explicit observation implementation, not a
chat timer or periodic model prompt. Configurable v2 examples: queue 120s,
running 30s, stopping 15s, terminal cleanup 300s, unknown 60s; read errors use
bounded backoff. The actual detection bound includes query latency and platform
update delay. Do not promise instant push. Native platform events can replace
polling only after the official capability is actually qualified.

Queue/training waiting may last hours or days. Do not apply the short model-turn
timeout to it. Expected duration overruns produce a milestone/diagnostic, not an
automatic stop/restart. Cancellation requires its existing authority. Keep last
known task state and unavailable observation distinct; recover the same UID on
restart. Avoid repeated user notifications for unchanged states.

## Durable continuation policy

Newly initialized pipeline v4 hosts explicitly freeze `continuation_policy:
{version: 1}`. Existing active/frozen configurations keep their original contract.
The resident observes the original LPAI task UID at persisted phase-dependent due
times (normally 60s queued, 30s running, 15s finishing). These are provider reads
inside the owner, not scheduled chat messages; no qualified platform push is
claimed. A terminal status begins collection, not scientific analysis: single
worker logs, complete artifacts, checksums, split and metric must pass first.
Temporary absent terminal pods/logs/artifacts retain the same identity and a
persisted exponential retry deadline, from 30s to 900s. They never resubmit or
repeat an unknown model call. Missing permissions/integrity and unknown effects
are reported separately from normal queue/training waits.

`source/monitor.json` records the last actual provider read and first observed
terminal time even while collection is failing. The completion outbox is replayed
with its original identity. The owner records `result_handoff` and the exact
analysis job before calling the original SDM coordinator; Inbox completion wakes
its condition. No user reply or foreground chat delivery gates the next action.
The derived progress report exposes these timestamps, current task, retry phase
and active job. A result regression is retained and compared with the verified
incumbent; it is not a host stop condition or evidence of success.

Known completed plan/code refusals and no-progress implementation feedback may
seed a new read-only reviewed plan with the original objection/receipt. Repeated
identical evidence and proposal stall for new evidence; identities alone are not
progress. An initial failed task can enter explicitly bound preparation recovery
without being ranked as a low-scoring candidate. Protected interface, original
Guard, code review and new submission preflight remain mandatory. An unknown
model outcome cannot be converted into a fresh model invocation.

A blocked owner stays alive for control, with blocked health. Unexpected owner
exit shuts the HTTP host down with failure, allowing the original supervisor's
safe-boundary reconciliation. HTTP liveness alone is never research health.
Control/status/stop retain their original config/host identity but do not require
a still-present compute workspace. Neither thread supervision nor this policy
claims OS autostart or automatic delivery into the desktop's original chat.


New SDK reviews opt into `model_runner.sdk_recovery: {version: 1}` under runner
v4/SDK. The isolated Windows guard launches the base interpreter directly, so
its strict Popen PID check is valid even when the owner uses a venv redirector.
The pinned SDK still loads from its configured root. The helper must receive an
exact bound parent acceptance after readiness and before `turn/start`. A sealed
`sdk-turn-intent.json` records the original thread before that RPC; SDK threads
are persistent in this mode for original-identity readback after interruption.
Persistence alone is not a completed-result receipt or permission to retry.
Old ephemeral/unknown calls keep their original status and are never relabeled
as no-turn merely because their process is gone or thread/read is unavailable.

A source defect and a deliberately reviewed cold upgrade are engineering
intervention, not autonomous recovery. A bounded adoption may register additional
hash-verified evidence for a genuinely new review under a new frozen runtime;
that does not settle or replay an old unknown model call. Preserve old outputs,
unknown identities, source Task/Guard and the intervention log. Separate normal
continuation demonstrated after upgrade from whole-run unattended acceptance.
Official protocol: https://developers.openai.com/codex/app-server/ (thread/read
is read-only and does not resume; checked 2026-11-13).


SDK recovery v2 adds original-turn reconciliation to the same owner. After an
original SDK owner is proved empty, require its accepted startup receipt,
pre-RPC intent, exact active thread/turn and effective context. A separately
contained helper may issue only thread/read for that stored thread. It promotes
only that exact turn's completed JSON final answer through the original purpose
validator; unreadable, missing, active or ambiguous outputs remain unresolved with a

thread/resume or sends input. Legacy ephemeral unknown calls remain blocked.

A known finished coordinator that reported proposal-model-blocked can re-enter

model intents, input bindings and approvals are retained. Recovered output must

Preparation recovery is a distinct evidence path throughout, not just a planning

`diagnose` plan first routes to the original coordinator's existing-evidence
adapter, then returns to scientific review; it is not a model.py implementation
or a training submission. Missing new measurements remain unsupported until a
qualified adapter exists. Repeating diagnosis against identical verified results
without new evidence blocks explicitly instead of creating an endless replan.

Review input uses reversible shared-context deduplication. Every objection and

### Graceful host upgrade

Use the original host's `--control drain` to fence new dispatch, then inspect
`drain.quiescent`; existing jobs and model/Guard operations must finish and commit
receipts first. `--control stop` on a new host requests the same drain and stops
only after quiescence. It is not an immediate kill. `--control resume` releases a
drain that has no pending stop. New completion events are durably deferred while draining and replayed with
their original identities after resume or explicit same-host restart; duplicates
already accounted are acknowledged. Cold adoption refuses unaccounted deferred
events. Preserve the old stopped run.

A legacy host lacks this fence. Do not infer safe stop from a single idle snapshot.
If an interrupted read-only review has already been reconciled to its exact known
SDK terminal status, `research_coordinator_recovery.py --config OLD --job JOB`
can finish that original delivery through its original frozen coordinator. It
forbids live/platform modes, native pending Context, unresolved model calls and a
live original host. It never manufactures a training result or resends the model.

### Byte-bounded registered evidence v2

New initialization/cold freezes upgrade an existing registered-supplements v1
policy to `{version:2,mode:registered-supplements}`. Old frozen callers and their
v1 receipts retain the original line-only interpretation. Do not replay old
issued requests under a changed input or overwrite their original supplements.

V2 adds required `json_pointers` to evidence queries. An empty array requests
original complete lines; nonempty RFC6901 paths select exact JSON values. `*`
selects array members. A JSONL query addresses records with start_line/line_count;
a JSON document uses start_line=1,line_count=1 for field selection. It reads
only the packet's hash-bound registered sources. No arbitrary file/tool is added.

The host bounds each response near 32 KiB and the supplement at 64 KiB, retaining
whole records/fields rather than silently clipping an oversized line. It exposes
delivered_line_count, next_start_line, view, reason and source digest. A single
oversized record returns no bytes and asks for narrower fields. This is not a
complete-source view. Missing pointers are explicitly reported, never invented data.
The controller accounts supplied ranges separately for each field selection;
an identical range/field query cannot reread the same prefix after a partial
return. Follow the actual cursor, or select genuinely different fields.
Question wording and pointer ordering do not create new evidence. It reserves
space for metadata separately from the text payload. Missing fields return
missing_pointers so the reviewer can correct its query without an engineering
takeover; missing values cannot support an approval.

rephrasing an already-read range is not progress. No-turn input preflight stays
not-issued; issued calls still reconcile their original thread/turn.

For historical recipe decisions prefer historical-recipe-index/historical-recipes.
When reading historical-results.jsonl, request the actual needed UID/configuration,
final validation, code identity and result references instead of importing every
epoch trajectory. Both roles receive the same raw sources and actual requested
values; all prior objections remain. Curves remain available for targeted queries
when they could change the decision. Exact field projection is not a claim that
omitted fields were read, a narrative summary or permission to approve a gap.
ModelRunner's 256 KiB request and explicit SDK history budgets remain unchanged.
A truly insufficient packet blocks rather than truncating decisive evidence.
